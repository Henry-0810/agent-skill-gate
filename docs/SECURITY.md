# Security model and limitations

This describes the current cooperative CLI on macOS/POSIX. See [ARCHITECTURE.md](ARCHITECTURE.md) for data flows and [HANDOFF.md](HANDOFF.md) for dated verification and unfinished work. Portable Downloads helpers do not make the full gate native Windows compatible.

## What this project does

- Serializes promotion from an isolated completed submission (`READY`) instead of racing against a download still being written.
- Rejects symlinks, FIFOs, device files and VCS metadata in the *submitted snapshot*; constrains file counts and size.
- Hashes paths, modes and contents before and after scanning, and again before promotion, to detect ordinary race/modification errors. Promotion uses a same-filesystem rename.
- Runs NVIDIA SkillSpector (static-only) inside a constrained ephemeral Docker container: no host credentials, no network, read-only source mount, read-only root filesystem, limited CPU/RAM/processes, dropped capabilities.
- Automatic processing blocks on unavailable scanner, scan error, incomplete scan (`--fail-on-incomplete`), any nonzero exit, and any recommendation other than `SAFE`. Interactive setup/backup review additionally permits `CAUTION` only with explicit per-skill risk acceptance, recorded before promotion. `--safe-only` disables that manual exception. High/critical overall risk, invalid reports and explicit incomplete metadata cannot be approved. No overwrite of already-installed skill directories.
- Interactive review scans into separate jobs under `reviews/` without `READY`; background recovery cannot silently approve them. Original backups remain intact. Snapshot hashes are checked again after selection. A human may explicitly select the listed SAFE recommendations together; that concrete selection is logged before promotion. CAUTION remains a separate per-skill acceptance and never joins that group implicitly. No headless approve-all or piped-input mode is supported.
- Records a JSON scan report for every processed job and an event trail; quarantines rejected submissions. Sends a best-effort macOS desktop notification through `osascript`.
- Uses either explicit `process` invocations or an optional Watchman trigger to process submissions. `submit` queues a snapshot; CLI success alone does not establish promotion. Trigger registration does not prove actual event delivery.

The shared eligibility policy is `agent_review.scan_problem`: a valid finite score in 0–100 is required, scores above 50 and HIGH/CRITICAL **overall** severity are blocked, and automatic processing additionally requires SAFE. Individual finding severities are separate: an eligible SAFE result can still contain a HIGH finding. Review findings as well as the overall recommendation.

## Critical limits

1. **Not a MAC / filesystem firewall.** Watchman reports events after the fact; it does NOT intercept a write. A Claude/Codex/Cursor agent running with the same macOS UID and the same filesystem access as the human can bypass this program by writing directly to active symlinks, editing the vault, altering the gate executable or the Watchman configuration, or modifying a snapshot after it was scanned.
2. **TOCTOU hardening is best-effort, not a proof.** A malicious same-UID process can alter the snapshot in the narrow interval after final hash verification and before promotion, or create path/symlink races in ancestor directories. Link/review helpers use no-follow directory handles, but legacy `initialize` checks managed entries and uses path-based parent creation; not every entry point has identical ancestor protection. Truly enforceable separation needs separate Unix users/sandboxes and a vault owner whose privileges are denied to the untrusted agent. A privileged broker must accept only immutable snapshots from an unprivileged handoff mechanism; do not simply run this Python process as root.
3. **Static verdict != clean execution.** `--no-llm` disables semantic LLM inspection; `--network none` makes online OSV CVE lookups unavailable (SkillSpector may fall back to offline data). Risk scoring is a heuristic, not a cryptographic attestation or sandboxed execution of the submitted code. A malicious SKILL.md can include agent instructions and runtime behaviors static scans do not catch.
4. **Downloading/extracting is separately risky.** `git clone` should be treated as transferring content, not as approval. Do not run npx/npm installers, shell scripts piped from curl, Homebrew package installation scripts or skill-specific setup scripts as a means of fetching a skill. A malicious npm postinstall or curl|sh compromises the machine *before* this gate runs. ZIP/tar extraction needs separate traversal, symlink and bomb defenses. Automatic `submit` accepts an already-materialized directory under staging `build/`; the separate human review flow copies existing backup skills. Neither implements safe URL fetching or archive extraction.
5. **Coverage scope is limited.** Project-local skills, plugins, hooks, MCP configs, tool settings, editor extensions and ordinary executable packages are not automatically routed through these symlinks. A scanner of `SKILL.md` is not a scanner of all software supply-chain vectors.
6. **Containers are not perfect isolation.** Docker Desktop / Colima runs a Linux VM on macOS; the gate gives the scanner only a narrow read-only bind mount and no docker.sock, but an upstream scanner vulnerability, container-runtime bug or malicious scanner image remains possible. Pin and review NVIDIA's source commit and dependencies; never mount host secrets or enable networking to the scan by default. Scans use `--pull never`; a missing local scanner image blocks rather than downloading an image implicitly. The separate build script clones an explicit commit and runs `docker build --pull`; source pinning does not attest every fetched build dependency. A local image tag is mutable; image presence alone is not verification of its source or dependencies.
7. **Scanner updates and skill updates are manual.** Existing installed skill names are blocked rather than replaced. Build a distinct review/approval versioning and rollback workflow before automatically upgrading them.
8. **Audit reports are not tamper-evident.** Reports and scripts are held under the same user's writable filesystem. For stronger integrity, store signed append-only logs in an independently controlled location and periodically reconcile a vault inventory against approved hashes.
9. **Notifications are best-effort.** `osascript` notifications depend on macOS user session and Notification permissions. The on-disk report/quarantine record is the authoritative outcome.
10. **No promised full unattended security.** Allowing an agent to launch arbitrary terminal commands or write anywhere under `$HOME` negates this trust boundary. Restrict filesystem access via a separate macOS user/OS-level sandbox, and deny writing to the vault and the gate code at the OS boundary.
11. **Manual acceptance is a policy exception, not a clean verdict.** CAUTION approval retains the scanner's original rating. Finding text can itself contain misleading instructions; escaped terminal output prevents control-sequence rendering but does not make that text trustworthy. An agent running as the user could also invoke or manipulate the wizard. Interactive checks are a usability safeguard, not a separate OS identity. Existing vault entries are skipped without inspection; link verification and readiness checks do not inventory, attest or rescan their contents.
12. **Recovery and storage need supervision.** Review jobs, backups and quarantine copies are not automatically expired. Repeated declines/reviews consume disk space. Interrupted reviews remain inert, but a crash after promotion and before final reporting can need reconciliation against the vault. Reports/events are not an atomic transaction with filesystem promotion. Older scanner versions may omit completeness fields; those scans rely on their strict exit-code contract and are displayed as coverage unreported.
13. **Dashboards are historical evidence.** Markdown export reads saved JSON records and cannot install skills or replay approval. A skipped existing name has not been rescanned. Reports contain local source paths and findings and should be reviewed before sharing. Scanner-originated Markdown, HTML and control characters are escaped. Output is created exclusively rather than overwriting existing files; Downloads failure retains a local report. A dashboard is neither signed provenance nor proof that the current vault still matches an old scan.
14. **Resource cleanup has open gaps.** Inspection shows scanner output is fully captured before its size check, so that check does not bound host capture memory. The 300-second timeout terminates the Docker CLI without explicit container-ID cleanup, which may leave a container running. These are known implementation risks, not reproduced exploit claims.

## Repeatable testing and evidence

`setup --demo` runs the wizard with harmless skills in a fresh temporary profile. Default scanner results are fixed, labelled simulations; they prove no real scanner verdict. Real skills, backups, staging and Downloads are outside that profile. Watchman queries/registration/backlog processing and notifications are disabled in both demo modes. Normal exit/Ctrl-C removes the profile unless `--keep-demo`; forced termination can leave its printed scratch directory behind. Do not delete real staging or backups to reset a test.

`setup --demo --real-scan` uses the existing Docker connection and trusted local image on temporary samples; it does not isolate the Docker daemon itself or test Watchman event delivery. Neither demo mode establishes an OS permission boundary. Automated tests mock external services; see the handoff for which live checks have actually been verified.

## Proposed integration and hardening — not implemented

- **Integration:** A shared source-to-install API/CLI with safe fetching, potentially exposed through a local stdio MCP adapter. No URL installer, MCP server, agent-host hooks, Homebrew formula or dependency bootstrap exists yet. MCP makes a tool available; it does not force a model to use it or prevent direct filesystem writes. [AGENT_POLICY.md](AGENT_POLICY.md) is advisory and is not automatically configured by setup.
- **Enforcement, if selected:** A restricted agent sandbox or distinct installer identity protecting the vault, gate code/configuration and human approval authority; a sealed handoff and constrained promotion broker. Avoid giving the agent control over the installer or Docker socket. A same-user background service alone does not provide this boundary, and a model-supplied approval flag must not count as human consent. The current wizard does not configure such restrictions.
- **Release hardening:** Signed/pinned skill sources and versioned installs, provenance manifests, rollback, quarantine retention, tamper-evident logging, resource-cleanup fixes and live integration tests on supported platforms. These remain planned work, not properties of today's CLI.

## Reporting issues

Open a GitHub issue without secret keys or private skill contents. Avoid attaching a full scanner report if it includes sensitive local paths or code.
