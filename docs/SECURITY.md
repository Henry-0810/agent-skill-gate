# Security model and limitations

## What this project does

- Serializes promotion from an isolated completed submission (`READY`) instead of racing against a download still being written.
- Rejects symlinks, FIFOs, device files and VCS metadata in the *submitted snapshot*; constrains file counts and size.
- Hashes the snapshot before and after scanning to detect ordinary race/modification errors.
- Runs NVIDIA SkillSpector (static-only) inside a constrained ephemeral Docker container: no host credentials, no network, read-only source mount, read-only root filesystem, limited CPU/RAM/processes, dropped capabilities.
- Automatic processing blocks on unavailable scanner, scan error, incomplete scan (`--fail-on-incomplete`), any nonzero exit, and any recommendation other than `SAFE`. Interactive setup/backup review additionally permits `CAUTION` only with explicit per-skill risk acceptance, recorded before promotion. `--safe-only` disables that manual exception. High/critical overall risk, invalid reports and explicit incomplete metadata cannot be approved. No overwrite of already-installed skill directories.
- Interactive review scans into separate jobs under `reviews/` without `READY`; background recovery cannot silently approve them. Original backups remain intact. Snapshot hashes are checked again after selection. A human may explicitly select the listed SAFE recommendations together; that concrete selection is logged before promotion. CAUTION remains a separate per-skill acceptance and never joins that group implicitly. No headless approve-all or piped-input mode is supported.
- Records a JSON scan report for every processed job and an event trail; quarantines rejected submissions. Sends a best-effort macOS desktop notification through `osascript`.

## Critical limits

1. **Not a MAC / filesystem firewall.** Watchman reports events after the fact; it does NOT intercept a write. A Claude/Codex/Cursor agent running with the same macOS UID and the same filesystem access as the human can bypass this program by writing directly to active symlinks, editing the vault, altering the gate executable or the Watchman configuration, or modifying a snapshot after it was scanned.
2. **TOCTOU hardening is best-effort, not a proof.** A malicious same-UID process can alter the snapshot in the narrow interval after final hash verification and before promotion, or create path/symlink races in ancestor directories. Truly enforceable separation needs separate Unix users/sandboxes and a vault owner whose privileges are denied to the untrusted agent. A privileged broker must accept only immutable snapshots from an unprivileged handoff mechanism; do not simply run this Python process as root.
3. **Static verdict != clean execution.** `--no-llm` disables semantic LLM inspection; `--network none` makes online OSV CVE lookups unavailable (SkillSpector may fall back to offline data). Risk scoring is a heuristic, not a cryptographic attestation or sandboxed execution of the submitted code. A malicious SKILL.md can include agent instructions and runtime behaviors static scans do not catch.
4. **Downloading/extracting is separately risky.** `git clone` should be treated as transferring content, not as approval. Do not run npx/npm installers, shell scripts piped from curl, Homebrew package installation scripts or skill-specific setup scripts as a means of fetching a skill. A malicious npm postinstall or curl|sh compromises the machine *before* this gate runs. ZIP/tar extraction needs separate traversal, symlink and bomb defenses; this v1 only accepts an already safely materialized skill directory under `build/`.
5. **Coverage scope is limited.** Project-local skills, plugins, hooks, MCP configs, tool settings, editor extensions and ordinary executable packages are not automatically routed through these symlinks. A scanner of `SKILL.md` is not a scanner of all software supply-chain vectors.
6. **Containers are not perfect isolation.** Docker Desktop / Colima runs a Linux VM on macOS; the gate gives the scanner only a narrow read-only bind mount and no docker.sock, but an upstream scanner vulnerability, container-runtime bug or malicious scanner image remains possible. Pin and review NVIDIA's source commit and dependencies; never mount host secrets or enable networking to the scan by default. Scans use `--pull never`; a missing local scanner image blocks rather than downloading an image implicitly. A local image tag is mutable; image presence alone is not verification of its source or dependencies.
7. **Scanner updates and skill updates are manual.** Existing installed skill names are blocked rather than replaced. Build a distinct review/approval versioning and rollback workflow before automatically upgrading them.
8. **Audit reports are not tamper-evident.** Reports and scripts are held under the same user's writable filesystem. For stronger integrity, store signed append-only logs in an independently controlled location and periodically reconcile a vault inventory against approved hashes.
9. **Notifications are best-effort.** `osascript` notifications depend on macOS user session and Notification permissions. The on-disk report/quarantine record is the authoritative outcome.
10. **No promised full unattended security.** Allowing an agent to launch arbitrary terminal commands or write anywhere under `$HOME` negates this trust boundary. Restrict filesystem access via a separate macOS user/OS-level sandbox, and deny writing to the vault and the gate code at the OS boundary.
11. **Manual acceptance is a policy exception, not a clean verdict.** CAUTION approval retains the scanner's original rating. Finding text can itself contain misleading instructions; escaped terminal output prevents control-sequence rendering but does not make that text trustworthy. An agent running as the user could also invoke or manipulate the wizard. Interactive checks are a usability safeguard, not a separate OS identity. Existing vault entries are skipped without inspection; link verification and readiness checks do not inventory, attest or rescan their contents.
12. **Recovery and storage need supervision.** Review jobs, backups and quarantine copies are not automatically expired. Repeated declines/reviews consume disk space. Interrupted reviews remain inert, but a crash after promotion and before final reporting can need reconciliation against the vault. Reports/events are not an atomic transaction with filesystem promotion. Older scanner versions may omit completeness fields; those scans rely on their strict exit-code contract and are displayed as coverage unreported.
13. **Dashboards are historical evidence.** Markdown export reads saved JSON records and cannot install skills or replay approval. A skipped existing name has not been rescanned. Reports contain local source paths and findings and should be reviewed before sharing. Scanner-originated Markdown, HTML and control characters are escaped. Output is created exclusively rather than overwriting existing files; Downloads failure retains a local report. A dashboard is neither signed provenance nor proof that the current vault still matches an old scan.

## Recommended production hardening roadmap

- **v1:** This cooperative, fail-closed pre-install gate and consistent source/staging workflow.
- **v2:** Locked-down agent runner under a separate UID; master vault owned by a distinct installer identity and readable but not writable by the agent. Separate sealed handoff and constrained promotion broker. Avoid giving the agent control over the installer or the Docker socket.
- **v3:** Signed/pinned skill sources and versioned installs, provenance manifest, rollback, quarantine cleanup retention, tamper-evident logging and broader integration tests across platforms. Explicit per-skill `CAUTION` review is available in the current interactive setup flow.

## Reporting issues

Open a GitHub issue without secret keys or private skill contents. Avoid attaching a full scanner report if it includes sensitive local paths or code.
